================================================================================
ESCALATION COMPLAINT SYSTEM - WORKFLOW EXPLANATION (Updated)
================================================================================

This document details the complete, updated workflow of the Escalation Complaint
System, incorporating user registration, daily operations, complaint routing,
the automated escalation pipeline, resolution reporting, and notification system.

================================================================================
WHAT HAS BEEN UPDATED (Change Summary)
================================================================================

1.  DATA MODEL MIGRATION (Normalized References)
    - User.teamLeader field migrated from plain string (name/employeeId) to
      ObjectId reference. A legacyTeamLeader string field was added for backward
      compatibility during migration.
    - Complaint model now includes normalized ObjectId references:
        * assignedTeamLeader  -> ObjectId ref to User (Team Leader)
        * responsibleDepartment -> ObjectId ref to Department
        * departmentManager   -> ObjectId ref to User (Manager)
      The older string fields (teamLeader, targetDepartment) are preserved for
      legacy/backward compatibility.

2.  CATEGORY-BASED DEPARTMENT ROUTING
    - Each Category now links to a responsibleDepartment (ObjectId ref).
    - Department model includes a manager field (ObjectId ref to User).
    - When a complaint is created, the system looks up the Category document,
      finds the responsible Department, and auto-populates the departmentManager.

3.  TEAM LEADER AUTO-REASSIGNMENT ON LEAVE
    - When a Staff member files a complaint, the system checks if the assigned
      Team Leader has an active, approved Leave record for today.
    - If the TL is on leave, the system automatically assigns a Backup TL and
      records this in the complaint timeline.

4.  DEDICATED TEAM LEADER CONTROLLER & ROUTES
    - New /api/teamleader/* endpoints with full TL-specific features:
        * GET  /complaints          - Get complaints assigned to the TL with
                                      real-time SLA metrics (elapsed, allowed,
                                      remaining minutes, slaStatus, isBreached).
        * GET  /my-staff            - Get staff members reporting to the TL
                                      with per-member active/total ticket counts.
        * GET  /complaints/:id      - Get single complaint details with auth check.
        * PUT  /complaints/:id/status  - Accept (In Progress), Reject, Resolve, or
                                         Close a complaint with timeline + notification.
        * POST /complaints/:id/comment - Add a comment with timeline entry.
        * POST /complaints/:id/resolve-report - Submit a resolution report
                                                forwarded to the Manager.
        * PUT  /complaints/:id/escalate - Manually escalate a complaint to the
                                          Department Manager with a reason.

5.  RESOLUTION REPORTS & MANAGER REVIEW PIPELINE
    - Complaint model now includes a resolutionReports array:
        { solvedBy, solverName, solverRole, reportText, forwardedTo, isReviewed }
    - TL submits a resolution report -> forwardedTo = 'Manager'.
    - Manager reviews and either:
        a. Forwards the TL report to HR (PUT /forward-report, status = 'Pending HR Review').
        b. Submits their own Manager resolution report to HR
           (POST /resolve-report, forwardedTo = 'HR', status = 'Pending HR Review').
    - HR receives complaints with status 'Pending HR Review' via GET /api/hr/complaints.

6.  MANAGER CONTROLLER ENHANCEMENTS
    - Department-scoped visibility: Managers only see complaints routed to their
      managed departments (via responsibleDepartment match).
    - New endpoints:
        * PUT  /complaints/:id/reassign      - Reassign complaint to a different TL.
        * PUT  /complaints/:id/approve        - Approve the resolution.
        * PUT  /complaints/:id/close          - Close the complaint.
        * PUT  /complaints/:id/status         - Update status and/or priority.
        * POST /complaints/:id/comment        - Add a Manager comment.
        * GET  /tl-performance                - View Team Leader performance metrics
                                                (total/resolved/pending/escalated).
        * PUT  /complaints/:id/forward-report - Forward TL report to HR.
        * POST /complaints/:id/resolve-report - Submit Manager resolution report to HR.

7.  HR CONTROLLER ENHANCEMENTS
    - GET  /api/hr/stats              - Live dashboard stats from MongoDB.
    - GET  /api/hr/team-leaders       - List all Team Leaders with staff count.
    - POST /api/hr/team-leaders       - Create new Team Leader (auto-generates
                                        employee ID like TL001, TL002, ...).
    - PUT  /api/hr/team-leaders/:id   - Update Team Leader details.
    - PUT  /api/hr/team-leaders/:id/status - Activate/Deactivate a Team Leader.
    - GET  /api/hr/registrations      - List registration requests (filter by status).
    - PUT  /api/hr/registrations/:id/approve - Approve with department + TL assignment.
    - PUT  /api/hr/registrations/:id/reject  - Reject with mandatory reason.
    - GET  /api/hr/complaints         - Get complaints pending HR review.
    - GET  /api/hr/my-staff           - Get staff assigned to the logged-in TL.

8.  NOTIFICATION SYSTEM
    - In-app notifications stored in MongoDB (Notification model).
    - Notifications are sent automatically when:
        * A new complaint is created  -> to assigned TL and Dept Manager.
        * A complaint is resolved     -> to Staff and Dept Manager/TL.
        * A complaint is escalated    -> to Dept Manager (Stage 1) or
                                         Super Admin (Stage 2), and to Staff.
        * A complaint is reassigned   -> to Staff.
        * A resolution report is submitted -> to Manager.
    - GET /api/notifications, PUT /api/notifications/:id/read endpoints.

9.  SLA TIMER IMPROVEMENTS
    - SLA pause/resume: Setting status to 'Waiting on User' pauses the SLA
      (records slaPausedAt). Leaving 'Waiting on User' calculates the total
      paused duration and subtracts it from elapsed time.
    - totalPausedDuration field tracks cumulative pause time across the complaint.
    - Business-minutes calculation (Mon-Fri, 9AM-6PM) in production mode;
      plain wall-clock minutes in test mode (TEST_SLA env).

10. COMPLAINT LIFECYCLE ENHANCEMENTS
    - Staff can Cancel a Pending/Submitted complaint.
    - Staff can Reopen a Resolved/Closed complaint (sets it back to 'In Progress').
    - Staff can Submit Feedback (1-5 star rating + comment) on Resolved/Closed
      complaints.

11. SERVER & DATABASE IMPROVEMENTS
    - Automatic startup migration (migrateDatabase):
        * 'Employee' role renamed to 'Staff'.
        * Team Leader references resolved from names to employee IDs / ObjectIds.
        * Default Manager user (MGR001) auto-created if not present.
    - Database readiness guard: API routes return 503 until MongoDB is connected.
    - DNS configuration for Windows/MongoDB Atlas reliability.
    - Retry logic on MongoDB connection failure (5-second intervals).

12. ESCALATION CRON JOB
    - Runs every minute via node-cron.
    - Mutex lock prevents overlapping runs.

13. UI MODERNIZATION & REFACTORING

1. ROLES & HIERARCHY
--------------------------------------------------------------------------------
The system is built on a 5-tier role structure:
- Staff: Files complaints, logs daily attendance, requests leaves, provides
  feedback on resolved complaints, can cancel or reopen tickets.
- Team Leader (TL): Oversees Staff, approves/rejects leaves, resolves complaints,
  submits resolution reports to Manager, can manually escalate to Manager.
  Views SLA metrics and manages their team workload.
- Manager: Oversees Departments and TLs. Handles escalated complaints. Reviews
  TL resolution reports and forwards them to HR. Can reassign, re-prioritize,
  approve, close, and comment on complaints. Monitors TL performance.
- HR: Approves new registrations, assigns departments and Team Leaders,
  manages Team Leader records (create/update/activate/deactivate),
  tracks attendance, reviews forwarded resolution reports.
- Super Admin: Exercises global controls, manages metadata (departments/
  categories), and resolves critical double-escalated complaints.

--------------------------------------------------------------------------------
2. ONBOARDING & REGISTRATION WORKFLOW
--------------------------------------------------------------------------------
Step 1: Account Creation
        A new user signs up with name, email, employee ID, and password.
        Their default status is set to 'Pending'. isFirstLogin = true.

Step 2: HR Approval
        The user cannot log in immediately. The account registration appears
        in the HR dashboard (GET /api/hr/registrations?status=pending).
        HR must manually:
        - Approve the registration (status -> 'Active')
        - Assign a Department (ObjectId)
        - Assign an active Team Leader (ObjectId, resolved from name/empId/ID)
        - Optionally assign a designation and employee ID
        The user's registered role (e.g., 'Team Leader', 'Staff') is preserved.
        On rejection, HR must provide a mandatory reason (stored in
        rejectionReason, status -> 'Inactive').

Step 3: HR can also directly create Team Leader accounts
        POST /api/hr/team-leaders auto-generates Employee IDs (TL001, TL002, ...).

--------------------------------------------------------------------------------
3. DAILY OPERATIONS WORKFLOW
--------------------------------------------------------------------------------
A. Attendance Tracking
   - Staff clock in upon logging in (logs entry time).
   - Staff clock out at the end of their shift (logs departure).
   - The status is calculated based on timing (e.g., 'Present', 'Late').

B. Leave Application
   - Staff submits a leave request with type, dates, and reason.
     Default status: 'Pending Approval'.
   - The leave request is visible to the Team Leader (for staff in their team),
     Manager (for staff in their department), HR, and Super Admin.
   - If any one of these roles approves the request, it is marked as 'Approved'.
     Rejection sets the status to 'Rejected'.

C. TL Leave-Based Auto-Reassignment
   - If a Staff member files a complaint while their assigned TL has an active
     approved Leave record (covering today's date), the system automatically
     assigns the complaint to a Backup Team Leader and records this in the
     complaint timeline.

--------------------------------------------------------------------------------
4. COMPLAINT CREATION & ROUTING WORKFLOW
--------------------------------------------------------------------------------
A. Complaint Creation & Auto-Routing
   - A Staff member files a complaint with: category, subject, description,
     and priority (Low, Medium, High, Critical).
   - A unique Complaint ID is auto-generated (CMP0001, CMP0002, ...).
   - The system performs Category-Based Routing:
       1. Looks up the Category document in the database.
       2. Finds the Category's responsibleDepartment (Department ObjectId).
       3. Finds the Department's manager (User ObjectId).
       4. Sets assignedTeamLeader = the Staff member's teamLeader.
       5. Sets responsibleDepartment = the Category's linked department.
       6. Sets departmentManager = the Department's manager.
   - Initial timeline entry: 'Complaint Created'.
   - Notifications are sent to the assigned TL and the Department Manager.

B. Complaint Status Lifecycle
   Pending -> In Progress -> Resolved -> Closed
                          -> Waiting on User (SLA paused) -> resumes on status change
                          -> Escalated (SLA breached)
                          -> Rejected
                          -> Cancelled (Staff cancels a Pending/Submitted ticket)
   Staff can also Reopen a Resolved/Closed complaint (sets it to 'In Progress').

--------------------------------------------------------------------------------
5. TEAM LEADER RESOLUTION WORKFLOW
--------------------------------------------------------------------------------
A. Viewing Assigned Complaints
   - The TL dashboard shows all complaints assigned to them, with real-time
     SLA metrics: elapsedMinutes, allowedMinutes, remainingMinutes, slaStatus
     (On Track / Warning / Breached / Escalated / Resolved).
   - Dashboard stats: totalAssigned, pending, inProgress, resolved,
     criticalCount, escalatedCount, slaBreachWarningCount, slaAdherenceRate.

B. Working on a Complaint
   - TL accepts the complaint -> status changes to 'In Progress'.
   - TL can add comments with timeline entries.
   - If information is missing, TL sets status to 'Waiting on User'
     (this action pauses the SLA timer).
   - When the user responds, TL moves status back to 'In Progress'
     (this resumes the SLA timer and accumulates totalPausedDuration).

C. Resolving a Complaint
   Option 1: Simple resolution.
     TL updates status to 'Resolved'. resolvedDate is recorded.
     Notifications sent to Staff and Department Manager.
   Option 2: Submit a Resolution Report.
     TL writes a detailed resolution report via POST /resolve-report.
     The report is attached to complaint.resolutionReports with
     forwardedTo = 'Manager', isReviewed = false.
     Status -> 'Resolved', and the Manager is notified for review.

D. Manual Escalation
   - If a TL decides they cannot handle the complaint, they can manually
     escalate it to the Manager via PUT /complaints/:id/escalate.
   - Status -> 'Escalated', escalated = true, escalationLevel = 1.
   - Manager is notified with the escalation reason.

--------------------------------------------------------------------------------
6. AUTOMATIC ESCALATION WORKFLOW (SLA-BASED)
--------------------------------------------------------------------------------
The background escalation cron job runs every minute. It checks all active
(non-resolved) complaints against their SLA thresholds.

A. SLA Thresholds (Production Mode - Business Hours: Mon-Fri, 9AM-6PM)
     * Critical: 4 hours (240 minutes)
     * High:     24 hours (1440 minutes)
     * Medium:   48 hours (2880 minutes)
     * Low:      72 hours (4320 minutes)
   (Test/Dev Mode - Plain Clock Minutes)
     * Critical: 2 minutes
     * High:     5 minutes
     * Medium:   10 minutes
     * Low:      15 minutes

B. Stage 1 Escalation: TL -> Department Manager
   - Triggered when elapsed business minutes >= SLA threshold and the
     complaint is NOT yet escalated.
   - Actions:
       1. Status -> 'Escalated'.
       2. escalated = true, escalationLevel = 1.
       3. Timeline entry: 'Automatically Escalated to Department Manager'.
       4. EscalationLog created with complaint details and reason.
       5. Notification sent to Department Manager.
       6. Notification sent to Staff.

C. Stage 2 Escalation: Manager -> Super Admin
   - Triggered when a Level 1 escalated complaint exceeds its SLA threshold
     again (measured from the timestamp of the Stage 1 escalation event).
   - Actions:
       1. escalationLevel = 2, escalatedToSuperAdmin = true.
       2. Timeline entry: 'Automatically Escalated to Super Admin'.
       3. EscalationLog created.
       4. All Super Admin users are notified.
       5. Staff is notified that their complaint reached Super Admin.
       6. Super Admin resolves the ticket.

D. SLA Pause/Resume
   - 'Waiting on User' status pauses the SLA clock (slaPausedAt recorded).
   - Resuming from 'Waiting on User' calculates the paused duration and
     subtracts it from the elapsed time.

--------------------------------------------------------------------------------
7. MANAGER REVIEW & REPORT FORWARDING WORKFLOW
--------------------------------------------------------------------------------
A. Manager Dashboard
   - Shows complaints routed to the Manager's managed departments.
   - Stats: totalComplaints, pendingReview, inProgress, escalated, closed.

B. Complaint Actions
   - Reassign to another TL (PUT /reassign) -> status reverts to 'Pending',
     escalated = false. Staff notified.
   - Update status or priority (PUT /status) -> timeline entry added.
   - Add comments (POST /comment) -> timeline entry added.
   - Approve resolution (PUT /approve) -> status = 'Approved'.
   - Close complaint (PUT /close) -> status = 'Closed', escalated = false.

C. Report Forwarding to HR
   - Forward TL Report: Manager reviews the TL's resolution report and
     forwards it to HR (PUT /forward-report). Report marked isReviewed = true,
     forwardedTo changed to 'HR'. Complaint status -> 'Pending HR Review'.
   - Submit Manager Report: Manager writes their own resolution report and
     submits it directly to HR (POST /resolve-report). Status -> 'Pending HR Review'.

D. TL Performance Monitoring
   - GET /tl-performance returns per-TL stats: total, resolved, pending,
     escalated complaint counts across the Manager's departments.

--------------------------------------------------------------------------------
8. HR REVIEW WORKFLOW
--------------------------------------------------------------------------------
- HR sees all complaints with status 'Pending HR Review' via GET /api/hr/complaints.
- HR reviews the forwarded resolution reports and takes final action.

--------------------------------------------------------------------------------
9. RESOLUTION, FEEDBACK & CLOSURE
--------------------------------------------------------------------------------
- Once resolved, the Staff member receives a notification.
- Staff can:
    * Review the resolution details.
    * Submit 1-5 star feedback along with comments
      (PUT /api/complaints/:id/feedback).
    * Or Reopen the complaint if unsatisfied
      (PUT /api/complaints/:id/reopen -> status reverts to 'In Progress').
- The complaint can be closed by the TL, Manager, or Super Admin.

--------------------------------------------------------------------------------
10. NOTIFICATION SYSTEM
--------------------------------------------------------------------------------
- All notifications are stored in the Notification collection in MongoDB.
- Each notification links to a user (recipient) and optionally a related complaint.
- Events that trigger notifications:
    * Complaint created       -> TL and Dept Manager
    * Status changed to Resolved -> Staff (and Dept Manager/TL)
    * SLA Stage 1 escalation  -> Dept Manager + Staff
    * SLA Stage 2 escalation  -> all Super Admins + Staff
    * Complaint reassigned    -> Staff
    * Resolution report submitted -> Manager
    * Manual escalation       -> Manager
- Users can view notifications via GET /api/notifications.
- Users can mark notifications as read via PUT /api/notifications/:id/read.
